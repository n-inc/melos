# GitHub PR Creator

## 概要

このスキルは、Gitの変更内容とコミット履歴を分析し、GitHub CLIを使用してPRを作成または更新する。

このスキルを使用する場面：
- 新しいPull Requestを作成する
- 既存のPRのタイトル・説明文を更新する
- コミット履歴から適切なPR内容を自動生成したい

## 実行手順

### 1. 状況分析とブランチ確認

以下のコマンドを実行して現在の状態を確認：

```bash
git branch --show-current
git status --porcelain
git log --oneline --graph --decorate -n 20
git branch -r --contains HEAD
```

- mainブランチの場合はPR作成を中止してエラーメッセージを表示
- 現在のブランチ名を取得した後、`gh pr list --head <ブランチ名> --json number,state,url,baseRefName` で既存PRを確認
- 既存PRがある場合：
  - PR の URL を表示
  - `AskUserQuestion`を使って質問：「既存の PR がありますが、どうしますか？」
    - [a] PR を更新する
    - [b] 終了する
  - [b] の場合は終了、[a] の場合は後続のステップで説明文の更新を行う

### 2. ベースブランチの決定

- 既存PRがある場合：既存PRのbaseRefNameを使用
- 既存PRがない場合：
  - デフォルトは `main` ブランチ
  - ただし、以下の条件に該当する場合のみ、ユーザーに確認：
    - ブランチ名が `fix/` や `hotfix/` から始まり、かつ履歴に別の `feature/` ブランチが存在する場合
    - コミット履歴から明らかに別のfeatureブランチから分岐していることが確認できる場合
    - `git log --oneline --graph` で見た時に、直近でマージされたのがmain以外のブランチの場合
  - ユーザー確認が必要な場合のみ、`AskUserQuestion`を使って質問：
    ```
    このブランチはfeature/xxxから分岐しているようです。PRのベースブランチを選択してください：
    [a] main（通常のPR）
    [b] feature/xxx（検出された親ブランチ）
    [c] その他（手動入力）
    ```
  - それ以外の場合は自動的に `main` を使用

### 3. リモート同期の確認

- 必要に応じて `git remote -v` と `git status -sb` で追加確認
- 未プッシュのコミットがある場合は、次のステップへ

### 4. プッシュの実行

- リモートブランチが存在しない場合：現在のブランチ名を使って `git push -u origin <ブランチ名>` を実行
- リモートブランチが存在する場合：`git push` を実行
- プッシュ完了を報告

### 5. コミット履歴の分析

- ベースブランチからの差分コミット: `git log --oneline origin/<ベースブランチ>..HEAD`
- 変更統計: `git diff origin/<ベースブランチ>...HEAD --stat`
- 必要に応じて `git log <ベースブランチ>..HEAD --format="%h %s" --name-status` で詳細な変更内容を確認
- 既存PRがある場合: `gh pr view <PR番号> --json title,body` で現在のPRタイトルと説明文を取得

#### 5.1 変更コードの読み込み（必須）

コミットメッセージだけでなく、実際のコードを読む。

- 主要な変更ファイルをReadツールで確認
- 既存の関連コード（依存先、類似実装）も確認
- データモデル、スキーマ、型定義を理解

このステップを省略すると、背景・予備知識セクションが浅くなり、レビュアーにとって理解しづらいPRになる。

設計判断を記述するために、以下の観点でも分析する：
- **実装上の選択**: 複数のアプローチが考えられた箇所はあるか
- **既存コードとの関連性**: 変更が依存する既存の仕組みや制約
- **変更の影響範囲**: この変更が他の機能やコードに与える影響

### 6. PR タイトルの生成

- 複数のコミットがある場合：全体の目的を要約した日本語タイトルを生成
- 単一のコミットの場合：そのコミットメッセージを改善した形で使用
- プレフィックス（feat:, fix:, refactor: など）がある場合は維持

### 7. PR 説明文の生成

コミット履歴と変更内容から、レビュアーが設計判断を評価できる説明文を生成する。

#### 説明文の構成

**1. 概要（Summary）**
- 何を実現するかを1-2文で記述
- ユーザー視点での価値を明記

**2. 背景・予備知識（Background）**
- この変更を理解するために必要な既存実装の説明
- 関連する仕組みや制約の説明
- レビュアーが知らない可能性のある前提知識
- 技術的に分かりにくい部分の解説（なぜこのような実装になっているか）
- 一見複雑・非効率に見える箇所の理由（なぜそんな面倒なことをしたか）

**背景・予備知識の深さの基準**

「レビュアーがこのコードベースを初めて見る」と想定して書く。

十分な深さの例:
- データモデルの関係性と制約（ユニークインデックス、外部キー）
- フレームワーク固有のパターン（RLS, DataLoader, Relay楽観的更新等）
- セキュリティ対策の理由（IDOR, レースコンディション等）

不十分な例:
- 「モデルAはモデルBに紐づく」（理由がない）
- 「DataLoaderを使用」（なぜ使うのかがない）

**3. 設計判断（Design Decisions）**
実装にあたって行った重要な意思決定を記載：

- **検討した選択肢**: どのようなアプローチが考えられたか
- **採用した方針**: なぜこのアプローチを選んだか
- **トレードオフ**: この選択のメリット・デメリット
- **代替案が適する条件**: どういう場合は別のアプローチが良いか

設計判断がない単純な変更（typo修正、明らかなバグ修正など）の場合は省略可。

**4. 変更の詳細（Changes）**（オプション）
- 主要な変更点のリスト
- 複雑な変更の場合のみ記載

**5. 確認リスト（Verification Checklist）**

レビュアーが効率的に確認できるTODOリストを生成する。

構成:
```markdown
## 確認リスト

### 動作確認
- [ ] `/path/to/page` を開く
  - 期待通りの挙動か
  - エラー時のメッセージが適切か

### コードレビュー
- [ ] `file_path:line` - [確認観点]
```

生成ルール:
- **変更種別から確認項目を推定**
  - APIエンドポイント → エラーハンドリング、レスポンス形式
  - DBスキーマ → データ整合性、マイグレーション影響
  - 認証/認可 → セキュリティ観点での動作確認

- **効率的なグルーピング**
  - 関連する確認項目はネストしてまとめる
  - 同じ操作で確認できる観点はまとめる

- **確認観点の記載**
  - 「何を見るか」＋「どう判断するか」を簡潔に
  - ✅ 良い例: 「APIが正しいレスポンスを返すこと」
  - ❌ 悪い例: 「正しく動作すること」

#### 記述方針

- **わかりやすさ優先**: 簡潔さよりも理解しやすさを重視
- **前提から説明**: 「これはこういう仕組みでこうなっているから」という背景を含める
- **レビュー観点の明示**: レビュアーが何を確認すべきかがわかるように
- **コード詳細は不要**: コードを読まなくても設計の妥当性を判断できる内容に

#### 既存PRの更新時

- 既存の説明文をベースに、新しいコミット内容を反映して更新
- 変更点を明確にしてユーザーに提示（例：「セクションを追加」「表現を更新」など）
- 既存の構造を尊重しつつ、必要な情報を追加・修正

### 8. PR の作成または更新

- 生成したタイトルと説明文を表示
- `AskUserQuestion`を使って確認：「この内容で PR を作成してよろしいですか？（ベースブランチ: <ベースブランチ名>）」
  - [a] はい
  - [b] 修正する
- [a] の場合：
  - 新規作成：HEREDOCを使用して改行を含む説明文でPRを作成

    ```bash
    gh pr create --title "タイトル" --body "$(cat <<'EOF'
    説明文（改行を含む）
    EOF
    )" --base <ベースブランチ>
    ```

  - 更新：HEREDOCを使用して改行を含む説明文でPRを更新

    ```bash
    gh pr edit --title "タイトル" --body "$(cat <<'EOF'
    説明文（改行を含む）
    EOF
    )"
    ```

- [b] の場合：修正の要望を聞いて、タイトルや説明文を調整後、再度確認

### 9. 前提知識コメントの投稿

コードベースに詳しくないレビュアー向けに、このPRを理解するための背景情報をコメントとして投稿する。

#### 9.1 解説すべき内容

以下の観点で、PR説明文に登場する概念を解説する：
- プロジェクト固有のデータモデル構造とその設計理由
- 使用しているライブラリ・フレームワークの機能と使い方
- 制約やバリデーションの背景と対処法
- 複雑な処理フローの詳細な動作

#### 9.2 コメントの構造

```markdown
## 補足: 前提知識

このPRをレビューする際に役立つ背景情報です。コードベースに詳しい方は読み飛ばしてください。

### [概念1のタイトル]
- その概念が何か
- なぜそうなっているのか（設計理由）
- 今回の変更との関連

### [概念2のタイトル]
...
```

#### 9.3 解説の深さ

- 用語の定義だけでなく「なぜそうなっているのか」まで説明する
- 具体的なコード例を含める（特に「❌ これはできない / ✅ こうする」形式が効果的）
- 抽象的な説明ではなく、このPRの文脈に即した具体例を使う

#### 9.4 投稿方法

```bash
gh pr comment <PR番号> --body "$(cat <<'EOF'
コメント内容
EOF
)"
```

### 10. 完了報告

- 作成または更新された PR の URL を表示
- `gh pr view --web` を実行してブラウザで PR を開く

## 出力フォーマット

- 各ステップの実行内容を簡潔に日本語で報告
- 生成されたタイトルと説明文は見やすくフォーマット
- 質問は **Q:** で始め、選択肢は `[a] [b] [c]` 形式で提示
- ベースブランチは常に明示的に表示

## 注意事項

- mainブランチからは直接PRを作成しない
- PRタイトル・説明文は日本語で記載
- 既存PRがある場合は更新するか確認
- プッシュ前にリモートとの同期状態を確認
