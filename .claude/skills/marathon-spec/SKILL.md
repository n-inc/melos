# /marathon-spec

対話的なインタビューを通じて、最良のプロダクトマネージャーが作るような要件定義Specを作成する。Marathon自動実行（`npx marathon`）を前提とした成果物を生成する。

## 入力

<feature_description> $ARGUMENTS </feature_description>

## 核心原則

**「テンプレート埋め」ではなく「対話的な発見プロセス」**

優秀なPMが要件定義を行うとき、決まったフォーマットを順番に埋めていくのではなく、対話を通じてその機能に本当に必要な情報を発見していく。このスキルはそのプロセスを再現する。

## プロセス

### 0. 状況確認

Spec作成開始前に現在の状況を確認する。

**確認手順**:
1. `PRD.md` の存在確認（worktreeルート）
2. `PLAN.json` の存在確認（worktreeルート）
3. `PROGRESS.md` の存在確認（worktreeルート）
4. `HANDOFF.md` の存在確認（worktreeルート）

**既存ファイルが存在する場合**:
- 内容を読み込み、概要を抽出
- ユーザーに状況を報告し、選択肢を提示：
  1. 既存内容に追加・拡張（既存PRDと新機能を統合した新しいPRDを生成、PLANも再生成）
  2. 既存を破棄して完全に新規作成
  3. 作業を中止（誤って実行した場合）

**選択肢2「既存を破棄して完全に新規作成」の場合**:
- `PROGRESS.md` をリセット（`# Marathon Progress\n\n**Status**: Not started` に置き換え）
- `HANDOFF.md` が存在する場合は削除

**何も存在しない場合**:
- 「新規Spec作成を開始します」と報告
- 次のステップへ進む

### 1-7. メインプロセス

1. **理解**: 入力を読み、機能の大枠を理解
2. **調査**: 既存実装・仕様を徹底的に調査（調査エージェントを並列実行）
3. **インタビュー**: 調査で分からないこと・意思決定が必要な点のみ`AskUserQuestion`で質問
4. **終了判断**: 十分な情報が揃ったとAIが判断したらSpec作成に移行
5. **PRD作成**: 収集した情報を最も適切な形式で構造化
6. **保存**: `$(git rev-parse --show-toplevel)/PRD.md` と `$(git rev-parse --show-toplevel)/PLAN.json` に書き込む（絶対パスを使用）
7. **次へ**: `npx marathon` での自動実行を案内

## 調査エージェント

以下を並列で実行し、徹底的に調査する：

- **repo-research-analyst**: 既存実装・プロジェクト規約・類似機能
- **best-practices-researcher**: 外部ベストプラクティス・業界標準
- **spec-flow-analyzer**: ユーザーフロー・エッジケース分析

調査で得られた情報を踏まえて、インタビューでは調査で解決できなかった点のみを質問する。

## インタビューの方針

### 核心原則：調査ファースト

**まず調査で解決を試み、調査で分からないこと・意思決定が必要な点のみ質問する。**

技術的な実装方法・既存パターン・仕様は調査で解決する（質問しない）。ビジネス要件の優先順位やトレードオフを伴う判断のみユーザーに確認する。

### 質問の観点（固定順序ではなく、機能に応じて柔軟に選択）

- **目的・動機**: なぜこれを作るのか？何を解決したいのか？
- **ユーザー像**: 誰のためか？その人の現状の課題は？
- **成功の定義**: これがうまくいったとき、何が変わるか？
- **ユーザー体験**: どのような体験になるか？どう操作するか？
- **エッジケース**: 想定外の状況ではどうなるか？
- **スコープ**: 何をやらないか？境界はどこか？
- **トレードオフ**: 競合する要素があればどちらを優先するか？
- **技術的制約**: （必要な場合のみ）特別な制約はあるか？

### 質問の作法

**表面ではなく根本を探る**:
- 「何を作りたいですか？」で終わらず
- 「それがないと、今どんな問題が起きていますか？」と掘り下げる
- 「なぜ？」「それがないと？」で本質に迫る

**提案込みで質問する**:
- 「〜という選択肢がありますが、いかがですか？」
- 「〜と考えますが、合っていますか？」
- ユーザーの思考を助ける形で質問

**見落としを積極的に発見**:
- ユーザーが言及していないが重要な観点を提示
- 「〜のケースは考慮されていますか？」
- 「〜という可能性もありますが？」

**必要に応じて代替案を提案**:
- 「もしかすると〜の方が良いかもしれません」
- 「〜という別のアプローチもあります」

### 終了条件

**AIが以下を判断したら終了**:
- この機能のSpecを作成するのに十分な情報が揃った
- これ以上聞いても新しい情報が出てこないと思われる
- ユーザー体験と受入基準が明確になった

## PRD出力

### 形式

固定テンプレートではなく、その機能の理想像を伝えるために本当に必要な情報を、最も適切な構造で記述する。

**重要**: PRDは「What」と「Why」に焦点を当てる。「How」（技術的実装詳細）は含めない。

### 必ず含めるもの

- **概要**: この機能が何であるか（1-2文）
- **背景・動機**: なぜ必要か
- **ユーザー体験**: どのような体験になるか（ユーザー視点）
- **受入基準**: 完成の判断基準（検証可能な条件）

### 機能に応じて含めるもの

以下は必要な場合のみ含める。すべてを埋める必要はない：

- 詳細なユーザーフロー
- エッジケースと対応方針
- スコープ外の明示
- トレードオフの決定事項
- 未解決事項

**含めないもの**（実装時に柔軟に判断）:
- 具体的な技術的アプローチ
- ファイル構成・変更対象ファイル
- 使用するライブラリ・パターン

## タスク分解の原則

**コンテキストを保ちながら完了できる「適切な粒度」に分解する**

### 判断基準

1. **コンテキストウィンドウに収まる**: 大きすぎると途中で迷子になる
2. **関連する変更はまとめる**: 細かく分けすぎると、全体像を見失い一貫性が損なわれる
3. **検証可能な単位**: 完了したか判断できる境界で区切る

### 適切な粒度の例

**適切**:
- 認証機能のログインフロー一式（API + フロント + テスト）
- 管理画面の「ユーザー管理」機能（一覧・詳細・編集をセットで）
- 検索機能（UI + API + 基本的なクエリ実装）

**細かすぎる**（避ける）:
- CRUD操作ごとに別タスク（Create, Read, Update, Delete を個別に）
- フロントとバックエンドを別タスク（関連するものは一緒に）
- テストを別タスク（実装と同時にテストも書く）

**大きすぎる**（分割が必要）:
- 「認証システム全体」→ ログイン、サインアップ、パスワードリセット、2FA等に分割
- 「管理画面全体」→ ユーザー管理、設定管理、ログ閲覧等の機能単位に分割

### 迷ったときの指針

「この機能を実装するとき、途中で別の部分の実装を忘れそうか？」
- 忘れそう → まとめる（コンテキストを保つ）
- 忘れない＆大きすぎる → 分割する

## MARATHONループ用JSONプラン形式

### 基本構造

```json
[
  {
    "id": "1",
    "description": "タスクの説明（必須要件のみ）",
    "checks": [
      { "text": "型エラーがない", "type": "auto:typecheck", "passed": false },
      { "text": "UIが正しく表示される", "type": "browser", "passed": false, "screenshot": "" }
    ],
    "passes": false
  }
]
```

### フィールド説明

| フィールド | 必須 | 説明 |
|-----------|------|------|
| `id` | ○ | タスク識別子（連番またはセマンティック） |
| `description` | ○ | タスクの説明（必須要件のみ、実装詳細は含めない） |
| `checks` | ○ | 検証項目の配列 |
| `passes` | ○ | タスク完了フラグ（初期値: `false`） |

**重要**: `description` には必須要件のみを記載。実装詳細（approach, files, hooks等）は含めない。実装時はPRD.mdを理想像として参照し、柔軟に調整する。

### Check Item フィールド

| フィールド | 必須 | 説明 |
|-----------|------|------|
| `text` | ○ | 検証内容の説明 |
| `type` | ○ | チェックタイプ（下記参照） |
| `passed` | ○ | 完了フラグ（初期値: `false`） |
| `screenshot` | △ | スクリーンショット証拠のR2 URL（`browser` タイプ用） |
| `video` | △ | 動画証拠のR2 URL（`browser` タイプ用） |

### Check Types

| type | 説明 | 証拠 |
|------|------|------|
| `auto:rspec` | RSpec で自動検証 | 不要 |
| `auto:jest` | Jest で自動検証 | 不要 |
| `auto:typecheck` | 型チェックで自動検証 | 不要 |
| `browser` | ブラウザで確認 | **必須**（`screenshot` または `video`） |
| `manual` | 手動確認 | 不要 |

### Browser Check の証拠

`type: "browser"` のチェック項目は、完了時に証拠（R2 URL）が必須:

```json
{
  "text": "ログインフォームが正しく表示される",
  "type": "browser",
  "passed": true,
  "screenshot": "https://r2.example.com/evidence/login-form.png"
}
```

- プラン作成時: `screenshot: ""` または `video: ""` を指定（どちらの証拠が必要か）
- 検証完了時: URLを設定してから `passed: true` に

## 完了後

### 1. ファイル保存

worktreeルートに絶対パスで保存：
- `PRD.md` - PRD（理想像・ゴール）
- `PLAN.json` - MARATHONループ用JSONプラン

### 2. 次のステップを案内

PRD・PLAN作成後、以下を案内：
- `npx marathon` を実行してMarathon自動実行を開始

### 3. 出力形式

```
PRDとPLANが完成しました。

📄 保存先:
- PRD: PRD.md
- JSONプラン: PLAN.json

次のステップ:
Marathon自動実行を開始する場合は `npx marathon` を実行してください。
```

## 制約

**コーディングは行わない。** インタビューとSpec作成（PRD.md + PLAN.json）のみ。
