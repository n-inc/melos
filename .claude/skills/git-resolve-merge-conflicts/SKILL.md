# マージコンフリクト解決コマンド

## 現在のGit状況

!git status --porcelain
!git diff --name-only --diff-filter=U
!git log --oneline -5
!git branch -v

## 1. コンフリクト分析

上記のGit状況から、コンフリクトが発生しているファイルを分析し、以下の順序で処理を進めます：

### 基本分析項目

- コンフリクトファイルの特定と種類分類（コード/設定/ドキュメント）
- 各ファイルの優先順位評価（ビルドエラーに影響するファイル → その他）
- コンフリクトの複雑さレベル（簡単な行追加 vs 大幅な構造変更）

### 詳細分析（ファイルごと）

各コンフリクトファイルについて、以下のように分析して最適な解決方法を決めます：

1. **ファイルの種類を調べる**
   - ファイル名と中身を見て、どんなファイルか判断
   - 自動で作られるファイル vs 人が書くファイルを見分ける
   - プロジェクトで使っている技術を確認（package.jsonなどから）

2. **どう解決するかを決める**
   - 依存関係ファイル → コマンドで作り直す
   - プログラムファイル → 人の手で統合するかClaude編集
   - 設定ファイル → 慎重に人が判断
   - ドキュメント → 内容に合わせて適切に統合

3. **自信の度合いを評価**
   - 自信が高い（90%以上）→ 自動で実行
   - 自信が低い（90%未満）→ ユーザーに選択肢を提示
   - なぜそう判断したかの理由も説明

## 2. 解決の進め方

各コンフリクトファイルについて、自信の度合いに応じて以下の手順で解決します：

### 自信が高いファイルは自動解決

**自信が90%以上の場合、自動で実行:**

```text
🔍 {filename} を分析中...
📋 判定: {ファイルタイプ}（自信度: {%}%）
💡 解決方法: {解決方法の説明}
🤖 自動実行中: {コマンド}
✅ 解決完了
```

### 自信が低いファイルはユーザーに相談

**自信が90%未満の場合、詳しく分析して推奨案を提示:**

**Q:** `{filename}` のコンフリクトを解決しますか？

1. **分析結果**

   ```text
   🔍 {filename} のコンフリクト分析:

   📋 LOCAL（現在のブランチ）: {変更内容の要約}
   📋 REMOTE（マージ元）: {変更内容の要約}
   📈 状況: {何をしようとしているか・影響範囲}
   🔄 競合の種類: {別々の変更/同じ場所の違う修正/機能の重複など}
   ⚠️  注意点: {統合する時に気をつけること}
   ```

2. **おすすめの方法**

   ```text
   💡 おすすめ: [X] {おすすめの選択肢}
   理由: {なぜこの方法が良いかの説明}
   結果: {この方法を選ぶとどうなるか}
   ```

3. **どうするか選択**
   - [a] LOCAL側を採用 - {この選択の良い点と使い時}
   - [b] REMOTE側を採用 - {この選択の良い点と使い時}
   - [c] 両方を統合（おすすめ★） - {統合の方針と期待される結果}
   - [d] コマンドで解決 - {おすすめコマンドと理由}
   - [e] 手動で解決 - {手動が必要な理由}

### Claude Codeで統合編集

[c] 両方を統合 を選んだ場合：

1. **変更内容の分析**
   - 変更の種類（新機能/修正/削除/整理）
   - 他への影響範囲を確認
   - 矛盾しない統合方法を検討

2. **統合案を提示**
   - 具体的な統合後のコード内容を表示
   - なぜそう統合するかの理由を説明
   - **最終確認**: 「この内容で編集しますか？ (Yes/No)」

3. **編集を実行**
   - 承認後、実際にファイルを編集
   - コンフリクトマーカー（<<<< ====）を削除
   - 統合されたコードを適用

### コマンドで解決

[d] コマンドで解決 を選んだ場合：

1. **環境を調べる**
   - プロジェクトのルートディレクトリを特定
   - 使っている依存関係管理ツールを検出（npm/yarn/pnpm/cargo/bundle等）
   - プロジェクト設定ファイルを確認

2. **コマンドを生成**
   - ファイルタイプに適したコマンドを生成
   - 実行環境が安全かを確認
   - 副作用を予測して警告

3. **実行の流れ**

   ```text
   🔧 実行予定コマンド: {生成されたコマンド}
   📋 実行理由: {なぜこのコマンドが適切かの説明}
   ⚠️  影響範囲: {ファイル変更/依存関係更新等の予想される変更}

   このコマンドを実行しますか？ (Yes/No)
   ```

4. **実行と確認**
   - コマンド実行とリアルタイムログ表示
   - 実行結果の検証（期待通りの変更か確認）
   - エラー時の代替処理

## 3. 段階的検証

各ファイルのコンフリクト解決後：

### 自動検証項目

- **構文チェック**: mcp__ide__getDiagnosticsでエラー検出
- **関連テスト**: 変更ファイルに関連するlint/typecheckの実行
- **ビルド確認**: 重要なファイルの場合、関連ビルドコマンドの実行

### エラー対応

- 検証でエラーが発生した場合、具体的な修正案を提示
- 必要に応じて追加の編集を実行
- ユーザーと協議してエラー解決方針を決定

## 4. 完了処理

全てのコンフリクトが解決された後：

### 最終ステップ

1. **ステージング**: `git add` で解決済みファイルをステージング
2. **状況確認**: `git status` で全てのコンフリクトが解決されていることを確認
3. **継続処理**:
   - マージの場合: `git commit` の実行確認
   - リベースの場合: `git rebase --continue` の実行確認
4. **最終テスト**: プロジェクト全体のテストコマンド実行（任意）

## 5. 出力フォーマット

### 進捗表示

```text
🔍 コンフリクト分析: [完了]
📝 ファイル解決: [2/5] (src/app.js ✓, config.json ✓, docs/readme.md ⏳)
✅ 検証: [実行中...]
🎯 完了処理: [待機中]
```

### エラー報告

- 具体的なエラー内容とファイル位置
- 推奨される解決方法
- 次に取るべきアクション

### 成功報告

- 解決されたコンフリクトの総数
- 実行されたテスト結果
- Git状態の最終確認結果
